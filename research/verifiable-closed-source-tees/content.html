Verifiable Closed Source Trusted Execution Environments For High Risk Complex Applications.

Open source code has become a standard for decentralized protocols and is becoming standard for distributed systems relying on TEEs for trusted computing that intersect with blockchains.

While this is ultimately a good thing, the advent of commercial LLMs used for penetration testing raises serious concerns around big open source codebases where the LLM can be handed off the whole program source. While complex systems must carry such scans internally it’s not trivial to be always ahead of a better structured prompt in the hands of a malicious party. The bottom line; source code analysis became much faster thanks to LLM leading to an increase of vulnerabilities found in the program’s logic, typestructure, dependencies, etc.

This is promising for reaching much higher security standards, but also scary for complex systems that are high-risk such as financial applications, especially when they operate on decentralized venues by holding cryptographic keys that authenticate directly to user funds.

For such applications a thoroguh internal continuous scan and competitive bounty program is recommended even after internal audits, but the attack vector perists especially in this timeframe where pentesting using LLMs is still not widely explored and there’s likely many wildcards that one just can’t reasonably predict.

Additionally, closing source is not the only concern. LLMs are increasingly making reverse engineering of binaries accurate, and it’s thus only a matter of time until “vibe hacking” can be efficiently carried out on the binaries themselves.

Closed source code however offers no auditability and no trust, hence there’s virtually no use in relying on trusted computing for a “decentralized” system if we cannot trust whatever the measurements produce. Additionally, closing the source of a codebase which you must know is behaving in a certain way and not being even able to run the protocol yourself sounds like an impossibility in a decentralized system.

NB: throughout the document the word decentralized is used to describe a system that has the charateristics to potentially be decentralized, not that it effectively is decentralized.

I explain however how trusted execution environment enable for a fundamentally different perspective when it comes to closing the source of the program. By combining key concepts from the confidentiality and integrity guarantees of TEEs, formal verification, and a cerimony setup we map a non client-side reproducible measurement to a guarantee that the digest mapping to that measurement corresponds to a program whose execution logic is deterministically guaranteed to not break what is defined in the specification.

I observe how the biggest limit of such system is actually backdoors through specifications that purposefully do not inlcude conditions that are crucial but may be overlooked by a user that does not know how the system works at a low level. I solve this by requiring mandatory non-interference in the trusted verification step. While this works, it bloats the specification requirements requiring more effort from the development teams compared to just open sourcing the code. Another additional layer I research is collective assembly of the specification, where participants that are able to have verification fail with accepted properties are elegible for a bounty.

Lastly, I observe also how the attack surface gets dramatically reduced compared to source code analysis.

Why Formal Verification

This document focuses on formal verification techniques to restrain the program’s execution to a verifiable set of properties. While some degree of control over the execution can be carried through virtualized isolation technologies such as sandboxes, there are several limitations to this approach in comparison to what I propose with formal verification.

Some of the strongest arguments against sandboxing techniques:

  • the sanbox itself can be exploited.
  • context switches and virtualization kill performance.
  • sandboxing cannot verify most properties without a heavily host based virtual machine, at which point the obfuscation becomes minimal defeating the purpose of such a system in the first place.

The only advantage that sandboxing offers is that once the sandbox is assumed to be completely safe the guarantees are stronger than formal verification where the specification may not explicitly cover certain edges.

About LLMs

A natural question is whether AI models running inside a TEE could just replace the formal verification pipeline entirely; i.e verifying properties directly through reasoning rather than deterministic proof. This might look like it reduces the formal methods expertise required, but it introduces a fundamental problem: AI verification is non-deterministic, susceptible to hallucination and unsound reasoning, and offers no hard guarantee of convergence. I actually invert this relationship in the protocol I propose here. Rather than replacing deterministic verification with AI, I use deterministic verification as an anchor that makes AI safe to deploy in the surrounding workflow. The non-determinism of AI is absorbed at the spec boundary; whatever property the AI proposes either passes or fails deterministic verification, and that result is reproducible and unchallengeable for a given specification. This gives the AI a tight feedback loop; propose a property, observe the deterministic outcome, refine, re-submit, essentially the formal verification system becomes an objective oracle for property satisfaction that grounds whatever creative exploration the AI is doing. Worth noting tho that this oracle only tells you whether a property holds, not whether it’s meaningful or security-relevant; the relevance filter comes from mechanisms I describe below.

AI is useful at two slightly different points in this protocol. First, for honest developers crafting their own specifications: an AI model can systematically map a codebase to a formal spec, surfacing properties the developer might not think to declare. This is the cooperative case where developer genuinely wants to maximize the trust guarantee for their users, and the deterministic pipeline serves as a backstop ensuring the AI-generated spec actually holds against the code. Second, and this is actually the more interesting case, AI strengthens the collective speccing mechanism I described earlier. External participants can use AI to blackbox-guess what properties \(S\) might be missing based on domain expertise and observable behavior (e.g API surface, documented functionality, known patterns for the application category), accepting the stake risk if they’re confident in the findings. That said the more powerful variant is running an audited, sandboxed LLM inside a proof-of-cloud TEE that has direct access to the source code during the collective speccing window. This TEE-hosted model can execute multiple adversarial rounds of auto-research against the code; proposing candidate properties, checking them against the existing spec for redundancy, and refining iteratively, all without the source ever leaving the enclave. What leaves the enclave are the proposed properties themselves, which reveal behavioral facts about the program (i.e what it must guarantee) without exposing implementation details (i.e how it does it); since the formal specification language constrains predicates to input/output behavior, properties structurally cannot reference internal state. This is the intended trust signal, not a confidentiality violation.

NB: the LLM image must itself be audited and reproducible so that participants can verify the model running inside the TEE is the expected one. I’m slightly hand-waving the auditing complexity here; what “audited” means operationally for an LLM is still a bit of an open question, but at minimum it means a reproducible image whose hash participants can independently verify.

I think the right architecture for the AI layer is actually pyramidal rather than a flat committee. You have an open model sitting at the base; it runs inside the TEE with full access to the source code and the existing specification \(S\), and it does the heavy lifting, proposing candidate properties through adversarial auto-research against the code, iterating across rounds. Above it sits a frontier model that never touches the source code but receives the proposed properties and evaluates them against \(S\) for redundancy and whether they’re actually meaningful as security properties, i.e a pre-filter before anything hits the formal verification pipeline. This separation isn’t arbitrary tho; it maps trust boundaries to capability tiers. The open model is inside the enclave with secrets so it must be auditable and reproducible; that’s feasible for open-weight models but not for proprietary frontier models. The frontier model only ever operates on public-facing formal properties so it never needs enclave access and its opacity is acceptable.

The pyramidal structure also enables something a flat committee just doesn’t have, which is a training dynamic. The open model doesn’t just propose and forget; it actually accumulates domain competence across rounds because it trains on feedback from three sources: the frontier model’s redundancy/validity judgments, the verification pipeline’s deterministic pass/fail results, and the structure of the confidential code and specs it has access to inside the enclave. Essentially the open model gets meaningfully better at proposing properties that are novel, valid, and security-relevant over successive rounds rather than starting from scratch each time. I think the frontier model’s feedback is a slightly underappreciated piece here; it encodes reasoning about what actually constitutes a meaningful security property for the application category, knowledge that the deterministic verifier alone can’t provide since it only answers “does this hold” not “does this matter.” The verification pipeline gives you correctness but the frontier model is what gives you relevance.

Given that constraint, this allows AI to heuristically improve specification coverage with full context (source + spec) under a trust model that doesn’t require trusting whoever initiated the query. The frontier model’s pre-filtering for redundancy and validity, combined with independent frontier model instances scoring proposed properties on safety-importance, means the system filters toward specifications that are not just satisfiable but actually meaningful. Turns out this combines well with the staking mechanism that penalizes trivial or redundant submissions; you end up with three complementary filters that cover different axes: deterministic verification catches incorrect properties, economic stake discourages unserious submissions, and the frontier model layer filters for both redundancy and relevance. The core security guarantee remains strictly deterministic; AI operates purely in the spec-crafting layer where its non-determinism is contained by the verification pipeline below it, tho it’s worth being explicit that verification eliminates false positives (properties that don’t actually hold) but not false negatives (important properties never proposed). The completeness of spec coverage ultimately depends on the collective speccing incentive structure, not on the verification pipeline alone.

Overview

I will first describe the protocol at a high level and the goals and non goals of the system, then go over the specific components one by one.

The proposed protocol is simple in its structure; developers upload their code and associated specification to a distributor trusted execution environment that will only share the compiled program with designated nodes and will only distribute the source code to entities that satisfy the developer’s conditions. A set v of verifier TEEs will then request the source code; in the base protocol each \(v_i\) receives the full source inside its own enclave and verifies independently, with confidentiality relying on the TEE hardware guarantees. An aspirational extension using MPC to split the source across \(v_i\) so that up to f compromised chips don’t break confidentiality is discussed in 1 but remains a research direction. v then executes the formal verification program against the provided spec. If the verification against the provided specification passes then the measurement of the compiled binary is endorsed by v. Once the endorsement is granted it cannot be revoked unless a contradicting more recent signature from v is provided 2, in which case we assume that the newer signature overwrites the previous one.

NB: For the scope of this document, whoever operates the above TEE must be directly trusted by the operator not to physically compromise the chip and thus gain access to the source code. In a scalable protocol, the distributor TEE is actually a set of nodes respecting a certain defined topology 3 splitting the work through MPC so that at least \(f\) of those chips must be physically compromised to break source code integrity.

Security Goals

The system provides bounded behavioral guarantees for closed-source programs; given a formal specification S and input bounds B_max, a quorum of k-of-N verification TEEs proves that the program with measurement M satisfies S for all inputs within B_max. The source code remains confidential (never leaves TEE hardware) and is destroyed after verification.

The guarantee holds as long as less than k verification TEEs are physically compromised. For information flow properties, the specification is complete by default as non-interference is mandatory in the trusted verification step, making sure that no undeclared data leakage exists. For all other property classes, the guarantee is limited to what S explicitly declares.

Out of Scope: Non-Goals

The following scenarios are not considered in this document:

  • Access to source code thorugh social engineering of dev teams / privileged team access. We assume that the codebase is behind NDA and the dev team is honest.
  • Compromise of the trusted setup that verifies the specification.

The Trusted Cerimony

Setup Phase

The developer (D) publishes the measurement (M) of the binary, a specification composed of a set of properties \(S = \{P_1, .., P_n\}\) expressed in a formal specification language and input bounds \(B_{max}\) defining the max input sizes up to which the properties must hold.

NB: the binary must be a reproducible build.

The verification node set \(v\) is deined and provisioned according to the required quorum topology4. Each node \(v_i\) in \(v\) boots with the open-source verification software and produces quotes so that external users can validate that \(v\) is indeed a trusted setup. \(v_i\)’s boot also creates the “attested” keypair whose public key (\(pkey_i\)) is placed in the quote as report data.

NB: quorum topology specification already accounts for the various potential properties that the trusted setup must guarantee, for instance all \(v_i\) in \(v\) must provide proof of cloud attestations or be operated by a select set of operators.

Lastly, \(D\) operates or places full trust into a distribution node, which may or may not be a TEE depending on \(D\)’s threat model.

Source Code Submission

\(D\) sends the source code to the distribution node, which distributes it to each \(v_i\) over an encrypted channel. Each \(v_i\) receives the full source inside its enclave and executes the verification pipeline independently.

Verification (across \(v_i\))

The verification is carried across four steps and a final cleanup step:

  1. compilation and binding the measurement.
  2. semantic extraction.
  3. property verification.
  4. attestation.
  5. cleanup.

Compilation

The source code is compiled into the binary \(B\) and then we check \(H(B) = M\), with \(M\) being the publicly referenced measurement.

Semantic Extraction

Each \(v_i\) takes the source and lowers it to an intermediate representation, something like MIR, LLVM-IR, or a custom IR depending on the toolchain. From the IR we build the control flow graph \(G\), unroll all loops up to the bounds in \(B_{max}\), and inline all function calls to produce a fully expanded graph \(G'\). If any loop has data-dependent termination that exceeds \(B_{max}\) then \(v_i\) flags it and aborts for that property; we need the computation to be statically bounded or we simply can’t reason about it. The last step is flattening \(G'\) into a DAG of primitive operations: arithmetic, comparisons, memory ops, I/O. I call this the computation DAG \(CR\), and it’s the semantic object on which all the properties will actually be verified.

Intuitively this is essentially the same transformation that zkVMs do on execution traces, RISC Zero for instance unrolls RISC-V into an arithmetic circuit5. The key difference is that here we do it statically over all possible inputs within the bounds rather than for a single concrete trace, since we want to verify properties universally not just witness them for one run.

Property Verification

For each property \(P_i\) in \(S\), \(v_i\) runs the appropriate verification technique on \(CR\). I go through all the property classes the system should support here; the choice of verification technique is actually tightly coupled to the property class.

NB: the properties described below are the result of what needs to be checked in financial applications that handle user inventories starting from different kinds of mutation inputs, more specifically it’s centered around tplus’ core system as a result some properties may be missing for other kinds of applications.

  • Functional correctness. Bounded model checking over all inputs within \(B_{max}\) to verify that output matches a reference specification. Essentially “does the program do what the spec says.”

NB: for programs that interact with stateful external systems (blockchains, oracles, contracts), \(B_{max}\) should be defined with an environment model that captures the external system’s possible behavior sequences, not just value ranges. For example a blockchain node can reorg, return a different header than expected, or drop a confirmed transaction; an oracle can go stale or repeat timestamps. The environment model constrains the input space to traces the external system can actually produce so that BMC doesn’t waste verification budget on impossible scenarios or flag false positives for things that can’t happen.

  • Conservation. SMT solving on path constraints to verify \(\sum(\text{inputs}) = \sum(\text{outputs})\) on every path through \(CR\), obviously critical for applications where value must be neither created nor destroyed.
  • Fairness and symmetry. Equivalence checking so that output must be invariant under permutation of user identities at the same priority level, i.e if two users submit the same action at the same priority the system treats them identically regardless of who they are.
  • Information flow (base). Non-interference via self-composition so that changing any user’s private data must change no public output byte. This is a default-deny model.
  • Information flow (timing). Additionally checks that execution time is independent of private data at declassification points, which matters because timing side channels can leak information even when the output bytes themselves are clean.
  • Determinism. Structural check on \(CR\) itself, no non-deterministic nodes in the DAG, no \(\text{rand}()\), no time-dependent branches. If the program is non-deterministic verification is essentially meaningless since you can’t reason about all executions.

NB: non-determinism is inevitable at certain parts in most stacks, but those non deterministic values (ex: timestamps) won’t be non deterministic within the circuit we’re auditing, they’ll be the result of a trusted guest os call, which must be open source and thus decoupled from the verification we’re targeting here.

  • Absence of backdoors. Combines dead code analysis, unreachable path analysis, and non-interference to verify there are no hidden code paths and no undeclared output channels, essentially that the I/O surface is complete. This is actually one of the most important classes for the threat model I described earlier since a specification backdoor could intentionally omit a code path that exfiltrates data through a channel the properties don’t cover.
  • Temporal safety. State machine bounded model checking with \(K\)-step unrolling to verify invariants hold across all event sequences: lock expiry, nonce monotonicity, state transitions that must follow a specific order.
  • Liveness. The complement of temporal safety, bounded temporal logic with a bound \(T\) to verify that good outcomes actually occur within \(T\) steps, e.g a liquidation fires before insolvency or a lock gets released before timeout. Without this liveness property the system could satisfy all safety properties by simply doing nothing.
  • Cryptographic API usage. Structural, taint, and temporal analysis for things like nonce uniqueness, key isolation, correct parameter usage, tho this is not full cryptographic verification, just verifying correct usage of the APIs.
  • Arithmetic precision. Abstract interpretation and interval analysis to verify no overflow at intermediate steps and that rounding error stays bounded by some \(\epsilon\).

NB: each verification tool produces one of three results per property: PASS, FAIL with a counterexample, or INCONCLUSIVE for if bounds are exceeded or verification timeouts. \(v_i\) records all of these results which will then b e used to either sign a rejection or approval.

Attestation

If all properties pass, \(v_i\) produces \(\sigma_i = \text{Sign}_{v_i}(\text{"M satisfies } \{P_1, .., P_n\} \text{ for inputs up to } B_{max}\text{"})\) using the attestation-linked signing key. The signed message includes \(M\), the verified properties with their formal statements, \(B_{max}\), a timestamp, and \(v_i\)’s attestation chain proving it’s a fresh TEE running the verifier image.

If any property fails, \(v_i\) signs a rejection with the failing property (and maybe a counterexample?). The counterexample contains only input/output pairs demonstrating the violation so that \(D\) can see where their program doesn’t match spec i.e no source code leaks even on failure.

Cleanup, Aggregation, and Lifecycle

After signing, \(v_i\) securely erases everything: \(C\), \(B\), the IR, \(G\), \(G'\), \(CR\). After this step \(v_i\) holds only \(\sigma_i\).

An aggregator (which can be untrusted, e.g a smart contract or a public bulletin board) collects signatures from all \(N\) verification TEEs. The acceptance criterion is straightforward; at least \(k\) of \(N\) signatures affirm “\(M\) satisfies \(S\) for \(B_{max}\).” If met the aggregated attestation is published and becomes the publicly verifiable guarantee. If fewer than \(k\) affirm the ceremony fails and the developer must fix the code, update \(M\), and re-run.

The ceremony must be re-run whenever the production code changes (new \(M\)), the property specification \(S\) is updated, or the input bounds \(B_{max}\) are increased.

Between ceremonies the attestation remains valid as long as nothing has changed. In fact the attestation is essentially a snapshot saying “at this point in time, this set of trusted verifiers confirmed these properties for this exact binary”, thus any change to the inputs invalidates it and a revocation must be published6.

Correctness Analysis

Soundness

The central guarantee: if \(k\) or more honest \(v_i\) sign “\(M\) satisfies \(P\)” then the code with measurement \(M\) actually satisfies \(P\) for inputs up to \(B_{max}\). I walk through why this holds since it’s essentially a composition of three steps that each honest \(v_i\) performs independently. First \(v_i\) compiles \(C\) and checks \(H(\text{compile}(C)) = M\), so by collision resistance and deterministic compilation we know \(C\) is the actual source behind the production binary. Then \(v_i\) derives \(CR\) from \(C\) via a deterministic semantics-preserving transformation so that the DAG faithfully represents \(C\)’s behavior for bounded inputs. Then \(v_i\) runs a sound verification tool on \(CR\), i.e if the tool reports PASS the property actually holds on \(CR\)7. The composition chains: \(C\) maps to \(M\), \(C\) maps to \(CR\), \(P\) holds on \(CR\), and since \(CR\) faithfully captures \(C\)’s bounded behavior and \(C\) compiles to the binary with measurement \(M\) we get that \(P\) holds on production code.

A malicious developer can’t subvert this; submitting \(C' \neq C\) fails the measurement check, compromising fewer than \(k\) TEEs still leaves at least one honest \(v_i\) running the correct pipeline, and the verification tools are part of the open-source verifier image so they can’t be tampered with inside an uncompromised enclave.

NB: soundness holds only for inputs up to \(B_{max}\). For inputs exceeding the bounds (e.g an order book deeper than 10K orders) the properties are simply not verified, which is inherent to bounded verification. The developer must set \(B_{max}\) to cover realistic operating conditions.

Completeness, Binding, and Confidentiality

The protocol is not complete in the formal sense; there will be correct programs that the verification tools can’t prove correct due to timeouts, inconclusives, or imprecise abstractions. But this is a fundamental tradeoff of formal verification i.e you can’t have a tool that is both sound (e.g no false positives) and complete (e.g no false negatives) for arbitrary programs, so every practical verification tool picks sound-but-incomplete.

The guarantee is one-sided: if the tool says PASS the property definitely holds, but if the tool fails to prove it that doesn’t mean the program is broken, it might just mean the tool ran out of time or lost precision through abstraction. The tool will never give you a false PASS but it might give you a false FAIL i.e it’s conservative by design8.

Going back to binding, the attestation is bound to \(M\) by inclusion in the signed message so if the developer deploys code with a different \(M' \neq M\) the attestation simply doesn’t apply. Users verify both sides, the production TEE attestation shows \(M\) and the ceremony attestation covers the same \(M\).

Confidentiality is also guaranteed as it relies on the source code \(C\) being transmitted over an encrypted channel to each \(v_i\) and existing only inside the enclave. Under the TEE confidentiality assumption no party outside can extract \(C\), and after the ceremony everything is erased. The signed output contains only \(M\), the property list, and the bounds, i.e no code or intermediate representations are leakd.

That said a hardware-level compromise of a single \(v_i\) could still extract \(C\); I partially mitigate this by distributing code only to TEEs that show proof of cloud, i.e prove they’re running on secure datacenters. For scenarios where even this residual risk is unacceptable there’s the MPC research direction even tho it feels unfeasible 9.

Some Practical Examples

Below are some practical examples of how this model can be used to verify complex properties:

Information Flow

“Private user data never reaches unauthorized outputs.”

Information flow is actually the most nuanced property class I want to verify here. The naive approach would be taint analysis: tag private inputs (user balances, order details), tag public outputs (broadcasts, logs, unauthenticated responses), verify no tainted data reaches a public output without passing through an approved sanitizer. This is well-studied and efficient but it has a fundamental problem; taint analysis tracks data dependencies through known struct fields, so a malicious developer who controls the code can encode private data in ways the tracker doesn’t follow, e.g balance bits into response padding, timestamp low bits, or nonce selection. Taint analysis is proactive in properties that the developer wants to check but its utility is not bidirectional; it checks whether any dependency exist along paths the analyzer tracks. When the developer is adversarial, this is obviously not a viable option.

The right property for most systems is non-interference, i.e making sure that no undeclared output changes with changes to private inputs (ofc under the BMC). Formally:

\[\forall u \in \text{Users}, \forall I_1, I_2 \in \text{Inputs}(B_{\max})\],

if \(I_1 \equiv_{-u} I_2\) then

\[\text{output_public}(\text{Program}(I_1)) = \text{output_public}(\text{Program}(I_2))\],

where \(I_1 \equiv_{-u} I_2\) means the inputs are identical except for user \(u\)’s private data and \(\text{output\_public}\) is the projection of all program outputs onto non-authenticated channels. This formalization doesn’t care about code structure, function names, or field labels; it compares raw output bytes. If any byte changes as a function of private data, there is a violation.

To see why this is better than taint analysis, consider a developer who embeds a hidden endpoint so that if the hash of the request payload equals some backdoor constant the program returns an encoding of all inventories. Taint analysis might not flag that encoded output if the output field isn’t labeled as a “balance output” (the developer controls field names). Non-interference catches it: you run the program twice with different balances, send the backdoor request in both runs, observe that the output bytes differ. Even steganographic tricks, balance bits XOR’d into padding, encoded into message ordering, hidden in error message selection, all get caught because the raw bytes change as a function of balance so non-interference fails.

We can verify this by leveraging self-composition: essentially I construct a product program that runs the original twice, once with \(\text{private}_{u,1}\) and once with \(\text{private}_{u,2}\), sharing all other inputs \(I_{\text{shared}}\), then asserts that the public projections of both outputs are equal. I run BMC on this product program searching for any assignment within \(B_{\max}\) that violates the assertion. If no counterexample exists within bounds, non-interference holds. Cost is approximately \(2\times\) single-program BMC since the state space doubles.

NB: a stateful backdoor (e.g a counter that only leaks on the third invocation) might seem like it requires \(K\)-step unrolling to catch, but it doesn’t. The program’s state \(S\) (including the counter) is an input to each invocation, and BMC explores all possible values of \(S\) within \(B_{\max}\). So it will find the state where counter = 2, pair it with the backdoor payload, and discover that the public output changes when private data changes. No need to actually replay \(K\) events to reach that state.

The critical piece that makes this work is the complete I/O surface argument. The definition of \(\text{output\_public}\) must capture every byte that exits the process, not just “known” output channels. In a VM execution where each byte leaving the VM’s boundaries goes through a syscall (\(\text{write}\), \(\text{sendto}\), \(\text{sendmsg}\), etc.), the verifier can enumerate all I/O syscall nodes in the DAG and includes all of them in \(\text{output\_public}\) so that a developer cannot create a hidden output channel that escapes the check.

For instance, adversarial attacker tries to place a hidden TCP listener on a secret port? Its \(\text{write}()\) calls are syscall nodes in the DAG, which is complete as it contains every instruction that can execute and every I/O operation that can occur. For explicit data channels, there is nowhere to hide. Covert channels (timing, cache side channels, power patterns) are not covered by this base-level argument; those require timing-sensitive non-interference described in the subsection below (On timing interference & other side channels).

Of course, strict non-interference is not practical for any system that must make private-data-dependent decisions. For example, a margin check necessarily leaks whether \(\text{balance} \geq \text{required\_margin}\). We must in fact relax the property with explicit approved declassification points: non-interference holds except at declared points like \(\text{margin\_check}(u, \text{order}) \to \text{bool}\) and \(\text{solvency\_check}(u) \to \text{bool}\). The ceremony verifier enforces that only the declared declassification points exist; if the developer introduces an undeclared one the self-composition check finds it because output bytes change outside the approved points.

On timing interference & other side channels

This last, mostly theoretical section, extends the output model to include execution time so that \(\text{output\_public} = (\text{all output bytes}, \text{execution\_steps})\). This catches timing side channels, e.g processing takes longer when a user has more positions. Most real systems fail this property tho because it requires constant-time programming: fixed-iteration loops, no data-dependent branching on private values. It’s the strongest information flow guarantee but the hardest to achieve in practice. Verification uses the same self-composition approach but the assertion includes step counts; may actually be practical for small critical sections (critical is in relation to confidentiality not integrity here), often infeasible for entire programs10.

Fairness

“No two users with the same inputs get different treatment.”

Fairness verification checks that the program’s output is invariant under permutation of user identities at the same priority level. Formally: given two users with identical inputs (same balances, same orders, same priority), the program must produce identical outputs regardless of which pubkey they have. If swapping pubkey \(A\) and pubkey \(B\) while keeping everything else the same produces different results, there’s a fairness violation.

The immediate question is how this works when the identity space is effectively unbounded, e.g user pubkeys are \(2^{256}\) for secp256k1. BMC doesn’t enumerate inputs; it encodes the DAG as a set of constraints (a SAT/SMT formula) and asks the solver to find any assignment that violates the property. The solver works backwards from the constraint, so if there’s a branch on pubkey == X where X is some hardcoded privileged constant, the solver immediately produces a satisfying assignment where one user’s pubkey equals X and the other doesn’t. It finds the path algebraically (i.e not by brute force).

The same principle applies for runtime configuration and values as well; if the privileged pubkey comes from an env var rather than a hardcoded constant the solver has two unknowns (pubkey and env_var), sets them equal, and finds the violation. At compile time neither value is known but the solver doesn’t need concrete values, it just needs to find that there exists some assignment where two users with identical inputs get different outputs.

An interesting case is obfuscated privilege checks, e.g if H(\text{pubkey}) == C where H is a hash function with high complexity to be reversed. This may seem like a blind spot since solver can’t really reach the privileged branch, but theoretically this is handled by treating H as an uninterpreted function: the solver doesn’t reason about what H computes, just that it’s deterministic.

The constraint now becomes “does a pubkey where \(F(\text{pubkey}) = C\) exist?” and which the solver can abstractly solve with pubkey = \(z\) where \(F(z) = C\) without computing any preimage. This extends to arbitrary compositions as well; if the check is H(\text{pubkey}) \% 2 == 0 the entire expression can be abstracted as a single uninterpreted function \(G(\text{pubkey})\) and the solver reasons about it the same way. Any deterministic computation over inputs can be abstracted this way since the congruence axiom holds for all deterministic functions.

NB: the theoretical argument for uninterpreted function abstraction feels correct; such actions are deterministic so the solver can reason about reaching the state in an abstract manner without inverting hash functions or solving hard problems. That said I haven’t validated this against real BMC tooling or practical approaches.

Collective Speccing

The biggest limitation of this whole protocol is that the guarantee is only as good as the specification, and a developer who controls \(S\) can deliberately omit properties that would expose exploitable behavior, i.e leave a gap between what the code actually does and what \(S\) declares. Non-interference partially mitigates this for information flow since it’s a default-deny model that catches undeclared channels regardless of whether \(S\) mentions them, but for other property classes like functional correctness, conservation, temporal safety, an omission in \(S\) is essentially invisible to the verification pipeline. I think this is actually the most interesting problem in the whole design.

Collective speccing is an adversarial mechanism that turns specification completeness into a public bounty game; instead of trusting \(D\) to provide a complete \(S\), external participants can propose properties that \(S\) should include but doesn’t, and get paid for finding genuine gaps. I’ll walk through how this works and why it’s slightly harder to game than it looks.

A researcher who believes \(S\) is missing a property \(P_{\text{new}}\) submits it along with a collateral stake \(c\); the stake prevents spam since if \(P_{\text{new}}\) is trivial, already covered by an existing property, or nonsensical, the researcher loses \(c\). The submission is encrypted to the verification TEEs so that the property itself remains confidential during the review window. The developer team then has a bounded review period \(t\) to respond, and there are essentially three outcomes. If \(D\) acknowledges the gap then \(P_{\text{new}}\) gets added to \(S\), the researcher receives a bounty \(b\) plus their stake \(c\) back, and the ceremony must be re-run with the updated \(S\). Alternatively \(D\) argues that \(P_{\text{new}}\) is already covered by existing properties or is outside the system’s scope; the justification is recorded on-chain and the researcher can dispute, in which case the verification TEEs can actually run the property against the code to determine if it’s genuinely redundant. But the interesting one is the third outcome, and I think it’s the critical forcing function of the whole mechanism; if \(D\) does not respond within \(t\) then \(P_{\text{new}}\) becomes public automatically. Silence is treated as an admission that the property is valid but inconvenient, and once public any user can see what \(S\) was missing and make their own trust decision. \(D\) can request a bounded extension by posting their own stake \(c_D\), which buys additional review time but signals to observers that \(D\) is indeed evaluating the submission i.e not ignoring it.

Now obviously a developer might just reject the property and quietly patch the code to satisfy it, re-run the ceremony with a new \(M\), and claim the property was always satisfied. This is the most predictable bad faith play here. Turns out tho it’s defeated by the public record; every submission, whether accepted, rejected, or ignored, is persisted with a timestamp. If \(D\) rejects \(P_{\text{new}}\) at time \(t_1\) and then deploys a new \(M'\) at time \(t_2 > t_1\) where the updated code now satisfies \(P_{\text{new}}\), the timeline is publicly visible and the researcher’s original submission proves they identified the gap before \(D\) fixed it. A reputation system or arbitration mechanism can then enforce the bounty retroactively, or at minimum the developer’s bad faith is permanently on record for users evaluating trust. \(D\) can also preemptively submit internal findings as timestamped notes, i.e if a researcher later submits a property that \(D\) already documented internally, \(D\) reveals the note to prove prior knowledge and avoid duplicate payouts. These notes are committed as hashes and only revealed when needed so they don’t leak information about known gaps before they’re fixed.

When a disputed property is run against the code and verification fails, i.e the code genuinely violates \(P_{\text{new}}\), the result is a confirmed vulnerability in live production code. The protocol must handle this as responsible disclosure: the failure result is held confidential for a remediation period \(t_{\text{fix}}\) during which \(D\) can patch and re-run the ceremony. Only after \(t_{\text{fix}}\) expires without a fix does the failure become public. The researcher receives their bounty immediately upon confirmed failure regardless of whether \(D\) patches in time.

There’s actually a secondary argument for collective speccing beyond completeness that I think is a bit underappreciated. Source code analysis with LLMs, the threat I motivated this whole document with, operates on a massive attack surface; every function, every branch, every interaction in the codebase is a potential target. Specification-level analysis operates on a dramatically smaller surface. A researcher looking at \(S\) can only reason about what properties are missing from a formal specification, not about buffer overflows or race conditions in implementation details they can’t see. The attack surface dramatically reduces from “all possible bugs in the code” to “all possible omissions in the spec.”

NB: this collapse is significant because it makes the problem tractable for both sides; defenders can actually enumerate what the spec covers, and attackers are constrained to a formal language rather than arbitrary code exploration.
